# ขอบเขตและบันทึกส่งมอบ

รุ่นวันที่ 10 กันยายน 2569 สำหรับมหาวิทยาลัยรับไปดูแลและพัฒนาต่อ

## ขอบเขตที่ส่งมอบ

> ระบบรองรับการยื่นและพิจารณาคำขอ จัดการทะเบียนบัญชีและโดเมน รวมถึงบันทึกการต่ออายุบริการ โดยการดำเนินการบนเครื่อง Hosting ยังอยู่ในความรับผิดชอบของเจ้าหน้าที่ และสามารถพัฒนาการเชื่อมต่อ API เพิ่มเติมได้ในอนาคต

ชุดนี้ประกอบด้วยซอร์ส Laravel/Blade, migrations, ข้อมูลแพ็กเกจตั้งต้น, ข้อมูลสาธิตสมมติแบบเลือก seed, automated tests, คู่มือใช้งานและติดตั้ง, สคริปต์สำรองข้อมูล และสคริปต์สร้าง ZIP พร้อม manifest/SHA-256

ไม่รวม credentials, ฐานข้อมูลจริง, ไฟล์ผู้ขอ, ข้อมูลบุคลากรจาก Plesk เดิม, vendor/node_modules หรือประวัติ Git หากหน่วยงานต้องรับข้อมูลจริงให้ส่งผ่านช่องทางที่ผู้ดูแลกำหนดแยกจากชุดซอร์ส

## งานที่เก็บก่อนส่งมอบ

- คำขอสาธารณะสร้างข้อมูลผู้ยื่นแยก ไม่เขียนทับผู้ขอในคำขอเก่า
- การแก้คำขอที่ใช้ applicant ร่วมกันแยก snapshot ก่อนแก้
- อนุมัติเฉพาะ submitted, บันทึกพร้อมประวัติใน transaction และไม่เพิ่มประวัติซ้ำเมื่อกดอนุมัติซ้ำ
- สร้างบัญชีหลังอนุมัติเท่านั้น ตรวจซ้ำใน transaction และบันทึกชื่อเจ้าหน้าที่จาก session
- หยุดการสร้างเลขใบเสร็จอัตโนมัติขณะอนุมัติ คงค่าเก่าไว้พร้อมป้ายว่าต้องตรวจสอบการชำระ
- ใช้ระดับประวัติ staff สำหรับรายการใหม่ แทนการระบุว่าทุกคนเป็นผู้อำนวยการ
- เลขคำขอใหม่ใช้ request_id แทน count() เพื่อไม่ให้จำนวนแถวหรือการลบรายการทำให้เลขวนซ้ำ
- ไฟล์ใหม่เก็บ private และมี route เปิดไฟล์สำหรับเจ้าหน้าที่ที่ active พร้อมคำสั่งย้ายไฟล์เก่าแบบตรวจเนื้อหา
- ตรวจเจ้าหน้าที่ที่ถูกปิดใช้งานในทุกการเข้าหลังบ้าน และกันปิดบัญชีตนเองผ่านหน้าแก้ไข
- ติดตั้งจากฐานข้อมูลเปล่าได้ แม้ไม่มีตารางบทบาทเก่า; ไม่มีรหัสผ่านเจ้าหน้าที่ตายตัว; seed master ซ้ำได้
- แก้ตัวพิมพ์ชื่อหน้าโดเมนสำหรับการติดตั้งบนระบบที่แยกตัวพิมพ์เล็ก/ใหญ่
- ทดสอบกระบวนการหลักทั้งฐานข้อมูล SQLite ทดสอบและ MySQL/MariaDB ชั่วคราว

## ข้อจำกัดที่ผู้รับควรทราบ

| เรื่อง | สถานะปัจจุบัน / งานต่อ |
|---|---|
| Plesk / VM / DNS | ไม่มีการเชื่อม API ทุกปุ่มเปลี่ยนข้อมูลในเว็บเท่านั้น |
| ตัวตนผู้ยื่น | แบบฟอร์มสาธารณะ ยังไม่มี SSO หรือยืนยันอีเมล; เจ้าหน้าที่ต้องตรวจคำขอ |
| สิทธิ์เจ้าหน้าที่ | ทุกบัญชี active มีสิทธิ์เท่ากัน; หากต้องแยกผู้ดู/ผู้อนุมัติ/ผู้ดูแล ต้องพัฒนาต่อ |
| การอนุมัติ | ชั้นเดียว ยังไม่มีเส้นทางปฏิเสธพร้อมเหตุผล ส่งกลับแก้ไข หรือผู้ลงนามหลายระดับ |
| ค่าใช้จ่าย | มีราคาอ้างอิงและการขอยกเว้น ไม่มีรับชำระจริงหรือออกใบเสร็จที่ตรวจสอบแล้ว |
| ต่ออายุ | ระดับบัญชีในทะเบียน ยังไม่รวมหลายบัญชีเป็น Subscription และไม่อัปเดต Hosting จริง |
| วันหมดอายุ | ยังไม่มีงานเปลี่ยนสถานะทะเบียนหรือแจ้งเตือนอัตโนมัติ ต้องตรวจวันที่ประกอบสถานะ |
| ประวัติ | มีอนุมัติและต่ออายุ ยังไม่มี audit log สำหรับทุกการแก้ไข/ลบ การแก้วันหมดอายุผ่านหน้าแก้ไขบัญชีไม่สร้างประวัติต่ออายุ |
| กู้คืน | ไม่มี soft delete; การลบสัมพันธ์แบบ cascade ต้องกู้จาก backup |
| ภาระงาน | ยังไม่มีผลทดสอบจำนวนผู้ใช้พร้อมกันหรือภาระ production; การทดสอบส่งซ้ำเป็นแบบลำดับ ไม่ใช่การจำลองคำขอพร้อมกันจริง |
| อีเมลและหน้าจอ | SMTP, เครือข่าย CDN, browser/mobile และ HTTPS ต้องตรวจรับบนเครื่องมหาวิทยาลัย |
| แพ็กเกจ / หน่วยงาน | ยังไม่มีหน้าจัดการ master data; ผู้ดูแลแก้ผ่านฐานข้อมูลหรือกระบวนการพัฒนาที่ควบคุมได้ |
| ข้อมูล legacy | importer รับ JSON ภายนอกและใช้รหัสผ่าน placeholder; ZIP ไม่รวม JSON ที่มีข้อมูลจริง |
| เวอร์ชันซอฟต์แวร์ | ล็อก dependencies ตามไฟล์ lock ที่ส่งมอบ ให้ผู้ดูแลประเมินการอัปเกรดและแพตช์ก่อนเปิดบริการสาธารณะ |
| เวลา | config/app.php ใช้ UTC ต้องกำหนดนโยบายแสดงเวลาไทยก่อนเปลี่ยนค่า และไม่ตีความ timestamp เก่าเป็นเวลาท้องถิ่นโดยอัตโนมัติ |

ข้อจำกัดเหล่านี้เป็นขอบเขตที่ยังไม่ได้ทำ ไม่ได้หมายความว่าการใช้งานบนเครื่องปลายทางผ่านการตรวจรับแล้ว

## แนวทางพัฒนาต่อ

1. กำหนดผู้ดูแลระบบ ช่องทางติดต่อ และนโยบายตรวจตัวตน/สิทธิ์เจ้าหน้าที่
2. เพิ่มติดตามคำขอและการแจ้งเตือนวันหมดอายุ
3. จับคู่บริการกับ Subscription จริงโดยมีรหัสเครื่องและรหัสบริการ แยกจากบัญชี FTP/SSH/Control Panel
4. เชื่อม API แบบอ่านข้อมูลก่อน แล้วทดสอบต่ออายุและระงับบนบริการทดสอบ พร้อม Queue, สถานะรอดำเนินการ และอ่านผลกลับ
5. หากต้องสร้าง VM ให้ทำตัวเชื่อมระบบ virtualization ของมหาวิทยาลัยแยกจาก Plesk
6. เพิ่มระบบรับชำระ/ใบเสร็จและ audit log ตามขอบเขตที่หน่วยงานกำหนด
